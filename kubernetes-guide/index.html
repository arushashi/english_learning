🚀 What is Kubernetes?

Before diving into individual pieces, here's the big picture.

Kubernetes (K8s)

Core Concept

Definition: Kubernetes is an open-source system that automatically deploys, manages, scales, and heals containerized applications across a group of machines (called a cluster). "K8s" is short for Kubernetes — there are 8 letters between the "K" and the "s".

💡 Think of it like: a building manager for an apartment complex (your servers). You tell the manager "I need 3 identical apartments ready for tenants (containers)," and the manager finds space, moves tenants in, replaces one automatically if it burns down, and adds more apartments if demand grows — without you micromanaging every unit.

Why people use it:
  • Self-healing — restarts failed containers, replaces them, kills ones that don't respond to health checks.
  • Scaling — automatically adds/removes running copies of your app based on demand.
  • Rolling updates — deploys new versions with zero downtime, and can roll back automatically if something breaks.
  • Portability — runs the same way on your laptop, on-prem servers, or any cloud (AWS, GCP, Azure).

Cluster

Core Concept

Definition: A cluster is the full set of machines Kubernetes controls: one or more control plane machines (the "brain") plus one or more worker nodes (the "muscle" that actually runs your applications).

💡 Think of it like: a company. The control plane is head office (planning, decisions), and worker nodes are the factories where the actual product (your app) gets made.

🏛️ Cluster Architecture

Kubernetes splits work between the control plane (decision-making) and nodes (execution).

Control Plane

Architecture

Definition: The control plane is the set of components that make global decisions about the cluster — scheduling, detecting failures, responding to events — and stores the cluster's entire state.

💡 Think of it like: air traffic control at an airport — it doesn't fly the planes (nodes do), but it decides where every plane goes and reacts when something goes wrong.

Its four main components:
  • kube-apiserver — the front door. Every command (from you, or from other components) goes through this REST API. It's the only component that talks directly to etcd.
  • etcd — a reliable, distributed key-value store that holds the entire cluster state (what should exist, and what currently does). Think of it as the cluster's "database" or "single source of truth".
  • kube-scheduler — watches for newly created Pods with no assigned node, and picks the best node for them based on resource needs, constraints, and policies.
  • kube-controller-manager — runs "controller" loops that continuously watch the cluster and nudge it toward the state you asked for (e.g. the ReplicaSet controller ensures the right number of Pod copies are running).
Check control plane health
# See control plane / node status
kubectl get componentstatuses
kubectl get nodes
kubectl cluster-info

Node & Node Components

Architecture

Definition: A Node is a worker machine (physical or virtual) that actually runs your application containers. Each node runs three key components that let it take orders from the control plane.

💡 Think of it like: a delivery driver. Head office (control plane) tells the driver what to deliver; the driver's own tools (kubelet, kube-proxy, container runtime) do the actual pickup, driving, and drop-off.

  • kubelet — an agent on every node that makes sure containers described in a Pod spec are actually running and healthy. It talks to the API server and reports node/pod status back.
  • kube-proxy — maintains network rules on each node so traffic sent to a Service reaches the right Pod, wherever it's running.
  • Container runtime — the software that actually runs containers (e.g. containerd, CRI-O). Kubernetes talks to it through the Container Runtime Interface (CRI).
Inspect nodes
# List all nodes with status
kubectl get nodes -o wide

# Detailed info: capacity, conditions, running pods
kubectl describe node <node-name>

# See resource usage per node (needs metrics-server)
kubectl top nodes

📦 Workloads

Workload objects describe what you want to run, and how many copies. Kubernetes keeps making it true.

Pod

Workload

Definition: A Pod is the smallest deployable unit in Kubernetes — a wrapper around one or more containers that always run together, on the same node, sharing the same network address and storage.

💡 Think of it like: a shared apartment. The containers inside are roommates — they share the same address (IP), can talk to each other over "localhost", and move in/out together. You almost never run a container directly in Kubernetes; you always run it inside a Pod.

Key facts:
  • Pods are disposable — if one dies, Kubernetes doesn't "fix" it, it creates a brand new one with a new IP.
  • You rarely create bare Pods directly — instead you use a Deployment/StatefulSet/Job which creates and manages Pods for you.
  • Most Pods run a single container; multi-container Pods are used for tightly-coupled "sidecar" helpers (e.g. a log shipper next to your app).
pod.yaml
# pod.yaml — a single Pod running nginx
apiVersion: v1
kind: Pod
metadata:
  name: my-first-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
Commands
# Create the pod from the YAML file
kubectl apply -f pod.yaml

# List pods
kubectl get pods

# See detailed status, events, container state
kubectl describe pod my-first-pod

# View logs
kubectl logs my-first-pod

# Open a shell inside the running container
kubectl exec -it my-first-pod -- /bin/sh

# Delete it
kubectl delete pod my-first-pod

ReplicaSet

Workload

Definition: A ReplicaSet's only job is to make sure a specified number of identical Pod copies ("replicas") are running at all times. If a Pod dies, it creates a replacement; if there are too many, it removes some.

💡 Think of it like: a headcount manager for a restaurant shift. They don't care which specific employee is on the register — they just make sure "3 cashiers" is always true, replacing anyone who calls in sick.

💡 In practice you almost never create a ReplicaSet by hand — you create a Deployment, and it creates and manages the ReplicaSet for you.
replicaset.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
Commands
kubectl apply -f replicaset.yaml
kubectl get replicasets
kubectl scale replicaset nginx-rs --replicas=5

Deployment

Workload

Definition: A Deployment describes the desired state of your app (which image, how many replicas) and manages ReplicaSets to get there. It adds rolling updates, rollbacks, and pause/resume on top of what a ReplicaSet does. This is the object you'll use most often to run stateless applications.

💡 Think of it like: a renovation project manager. You say "I want the store to look like design v2 instead of v1." The manager updates it room-by-room (rolling update) so the store never fully closes, and can put it back to v1 instantly if v2 looks wrong (rollback).

Deployment → ReplicaSet → Pod — a Deployment creates a ReplicaSet, which creates Pods. This layering is what enables safe rollouts: each new version gets its own ReplicaSet.
deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "250m"
              memory: "256Mi"
Commands
# Create / update
kubectl apply -f deployment.yaml

# Quick imperative create (no YAML)
kubectl create deployment nginx --image=nginx:1.27 --replicas=3

# Scale
kubectl scale deployment nginx-deployment --replicas=5

# Update the image (triggers a rolling update)
kubectl set image deployment/nginx-deployment nginx=nginx:1.28

# Watch rollout progress
kubectl rollout status deployment/nginx-deployment

# View rollout history
kubectl rollout history deployment/nginx-deployment

# Roll back to the previous version
kubectl rollout undo deployment/nginx-deployment

# Roll back to a specific revision
kubectl rollout undo deployment/nginx-deployment --to-revision=2

StatefulSet

Workload

Definition: Like a Deployment, but for applications that need a stable identity: predictable Pod names (app-0, app-1, app-2), stable network hostnames, and their own persistent storage that survives Pod restarts. Used for databases (MySQL, PostgreSQL, Kafka, etc.).

💡 Think of it like: numbered parking spots vs. a first-come-free-for-all lot. A Deployment's Pods are interchangeable (any spot works); a StatefulSet's Pods each have their own permanent, labeled spot (db-0 always keeps its own disk and name, even after a restart).

statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "web"
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          volumeMounts:
            - name: www
              mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
    - metadata:
        name: www
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
Commands
kubectl apply -f statefulset.yaml
kubectl get statefulsets
kubectl get pods -l app=web   # web-0, web-1, web-2

DaemonSet

Workload

Definition: Ensures that a copy of a Pod runs on every (or a chosen subset of) node in the cluster. When a new node joins, it automatically gets the Pod; when a node leaves, that Pod is cleaned up.

💡 Think of it like: installing a smoke detector in every room of a building. It's not about "how many copies" — it's "one in every room, no exceptions." Commonly used for log collectors, monitoring agents, and network plugins.

daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-log-agent
spec:
  selector:
    matchLabels:
      app: log-agent
  template:
    metadata:
      labels:
        app: log-agent
    spec:
      containers:
        - name: fluentd
          image: fluent/fluentd:v1.16
Commands
kubectl apply -f daemonset.yaml
kubectl get daemonsets -A

Job

Workload

Definition: Runs one or more Pods to completion for a task that finishes (unlike a Deployment, which runs forever). Kubernetes retries the Pod if it fails, until it succeeds or hits a retry limit.

💡 Think of it like: hiring a mover for a one-time house move, not a permanent employee. Once the move is done, the job is complete — no need to keep "restarting" it.

job.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: data-migration
spec:
  backoffLimit: 3
  template:
    spec:
      containers:
        - name: migrate
          image: my-migration-tool:1.0
          command: ["./migrate.sh"]
      restartPolicy: Never
Commands
kubectl apply -f job.yaml
kubectl get jobs
kubectl logs job/data-migration

CronJob

Workload

Definition: A Job that runs on a repeating schedule, using standard cron syntax (e.g. every night at 2 AM).

💡 Think of it like: a recurring calendar reminder that, instead of pinging you, actually runs the task for you — like a nightly database backup.

cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"   # minute hour day month weekday
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: my-backup-tool:1.0
          restartPolicy: OnFailure
Commands
kubectl apply -f cronjob.yaml
kubectl get cronjobs

# Manually trigger a run right now (for testing)
kubectl create job manual-run --from=cronjob/nightly-backup

🌐 Networking & Service Discovery

Pods get new IPs every time they're recreated — networking objects give you stable ways to reach them anyway.

Service

Networking

Definition: A Service gives a stable, unchanging network address (IP + DNS name) to a group of Pods, and load-balances traffic across whichever of those Pods are currently healthy — even as individual Pods are created and destroyed.

💡 Think of it like: a company's single customer-support phone number. Employees (Pods) come and go, sit at different desks (IPs), but the phone number never changes — calls always get routed to whoever's available.

Service types:
  • ClusterIP (default) — reachable only from inside the cluster. Used for internal service-to-service traffic.
  • NodePort — opens the same fixed port on every node, exposing the Service externally without a cloud load balancer. Good for testing.
  • LoadBalancer — asks your cloud provider (AWS/GCP/Azure) to provision a real external load balancer pointing at the Service.
  • ExternalName — maps the Service to an external DNS name (e.g. a managed database outside the cluster) with no proxying.
service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: ClusterIP
  selector:
    app: nginx        # routes to any Pod with this label
  ports:
    - port: 80          # port the Service exposes
      targetPort: 80     # port the container listens on
Commands
kubectl apply -f service.yaml
kubectl get services
kubectl describe service nginx-service

# Quick imperative way to expose an existing deployment
kubectl expose deployment nginx-deployment --port=80 --type=ClusterIP

# Forward a local port to a Service for local testing
kubectl port-forward service/nginx-service 8080:80

Ingress

Networking

Definition: Manages external HTTP/HTTPS access to Services inside the cluster, based on hostnames and URL paths — e.g. routing api.example.com to one Service and example.com/blog to another, using a single external IP. Requires an Ingress Controller (e.g. NGINX, Traefik) running in the cluster to actually work.

💡 Think of it like: a hotel receptionist. One public entrance (IP address), but the receptionist reads your request ("I'm here for Room 204" = a URL path/host) and routes you to the right internal room (Service).

ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80
Commands
kubectl apply -f ingress.yaml
kubectl get ingress
kubectl describe ingress app-ingress

Network Policy

Networking / Security

Definition: A firewall for Pod-to-Pod traffic. By default, all Pods can talk to all other Pods in the cluster; a NetworkPolicy restricts that, allowing only the traffic you explicitly permit.

💡 Think of it like: a office building where, by default, anyone can walk into any room. A NetworkPolicy is a keycard rule: "only people from Accounting can enter the Accounting server room."

networkpolicy.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
Commands
kubectl apply -f networkpolicy.yaml
kubectl get networkpolicies

DNS & Service Discovery

Networking

Definition: Kubernetes runs an internal DNS service (CoreDNS) that automatically gives every Service a resolvable name, so Pods can find each other by name instead of hardcoding IPs.

💡 Think of it like: a phone book that updates itself automatically. Instead of memorizing a number that keeps changing, you just look up "backend-service" and always reach the right place.

Standard DNS format: <service-name>.<namespace>.svc.cluster.local
  • From the same namespace, you can just use <service-name>.
  • From a different namespace, use <service-name>.<namespace>.
Commands
# From inside any pod, test DNS resolution
kubectl run -it --rm debug --image=busybox --restart=Never -- \
  nslookup nginx-service.default.svc.cluster.local

🗄️ Configuration & Storage

Keep configuration, secrets, and data separate from your application images.

ConfigMap

Config

Definition: Stores non-sensitive configuration data (key-value pairs, config files) outside your container image, so you can change settings without rebuilding the image.

💡 Think of it like: a settings sheet handed to a new employee on their first day, instead of tattooing the rules onto their skin. Change the sheet, not the person.

configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_MODE: "production"
  MAX_CONNECTIONS: "100"
Using it in a Pod
spec:
  containers:
    - name: app
      image: my-app:1.0
      envFrom:
        - configMapRef:
            name: app-config
Commands
kubectl apply -f configmap.yaml
kubectl create configmap app-config --from-literal=APP_MODE=production
kubectl get configmaps
kubectl describe configmap app-config

Secret

Config / Security

Definition: Like a ConfigMap, but for sensitive data — passwords, API keys, TLS certificates. Values are stored Base64-encoded (not encrypted by default — enable encryption-at-rest and RBAC for real protection).

💡 Think of it like: a locked drawer instead of an open desk (ConfigMap) — same idea of "config outside the app," but for things you don't want everyone glancing at.

⚠️ Base64 is encoding, not encryption — anyone with API access can decode it. Restrict access with RBAC and consider a secrets manager (Vault, Sealed Secrets) for production.
secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
stringData:          # stringData lets you write plain text; k8s encodes it
  username: admin
  password: SuperSecret123
Commands
kubectl apply -f secret.yaml
kubectl create secret generic db-credentials \
  --from-literal=username=admin --from-literal=password=SuperSecret123
kubectl get secrets
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d

Volume

Storage

Definition: A directory of storage attached to a Pod, accessible to its containers. Unlike a container's own filesystem, a Volume's lifetime can outlive individual container restarts within the same Pod (though a basic Volume still dies with the Pod).

💡 Think of it like: a shared USB drive plugged into the apartment (Pod) — if one roommate (container) restarts, the drive and its files are still there.

Example: emptyDir volume
spec:
  containers:
    - name: app
      image: my-app:1.0
      volumeMounts:
        - name: cache-volume
          mountPath: /cache
  volumes:
    - name: cache-volume
      emptyDir: {}

PersistentVolume (PV) & PersistentVolumeClaim (PVC)

Storage

Definition: A PersistentVolume is a piece of real storage in the cluster (a disk), provisioned by an admin or dynamically. A PersistentVolumeClaim is a request by a user/app for storage with certain properties (size, speed) — Kubernetes matches the claim to an available volume.

💡 Think of it like: a self-storage facility. The PV is an actual storage unit that exists; the PVC is your rental request ("I need 50 sq ft, climate controlled"). You don't care which physical unit you get — you just get one that matches your claim.

pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
Using the PVC in a Pod
spec:
  containers:
    - name: app
      image: postgres:16
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: data-pvc
Commands
kubectl apply -f pvc.yaml
kubectl get pv
kubectl get pvc
kubectl describe pvc data-pvc

StorageClass

Storage

Definition: Defines a "type" of storage (e.g. fast SSD vs. slow HDD, or a specific cloud disk type) and lets PersistentVolumes be created automatically ("dynamic provisioning") on demand, instead of an admin manually pre-creating them.

💡 Think of it like: a menu at a storage-unit rental office listing "Standard," "Climate-Controlled," "Premium" options — pick a class, and a matching unit gets built for you automatically instead of waiting for one to already exist.

storageclass.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
Commands
kubectl apply -f storageclass.yaml
kubectl get storageclass

🏷️ Namespaces & Resource Management

Organize the cluster and keep teams/apps from stepping on each other's resources.

Namespace

Organization

Definition: A way to divide one cluster into multiple virtual clusters — a logical grouping for resources, often used to separate teams, environments (dev/staging/prod), or projects. Object names must be unique within a namespace, not across the whole cluster.

💡 Think of it like: separate floors in the same office building. Floor 1 (dev) and Floor 2 (prod) can both have a desk named "Reception" without conflict — they're isolated by floor.

Commands
kubectl create namespace staging
kubectl get namespaces

# Run a command against a specific namespace
kubectl get pods -n staging

# Set a default namespace for your current context
kubectl config set-context --current --namespace=staging

Labels & Selectors

Organization

Definition: Labels are key-value tags attached to objects (e.g. app: nginx, env: prod). Selectors are queries that use those labels to find a group of objects — this is how Services, Deployments, and ReplicaSets know which Pods belong to them.

💡 Think of it like: colored stickers on boxes in a warehouse. A label says "fragile, kitchen" (a tag); a selector is the instruction "grab every box labeled 'kitchen'" — you don't need to know each box's exact location.

Commands
# Add a label to an existing pod
kubectl label pod my-first-pod tier=frontend

# Find objects by label
kubectl get pods -l app=nginx
kubectl get pods -l 'env in (prod,staging)'

# Remove a label
kubectl label pod my-first-pod tier-

Annotations

Organization

Definition: Like labels, annotations are key-value metadata — but they're for non-identifying information (build version, contact email, tool-specific config) and aren't used for selecting objects.

💡 Think of it like: a sticky note vs. a filing label. The label (filing category) is used to find the folder; the sticky note (annotation) just carries extra context — "reviewed by Priya on 3/1" — that no one searches by.

Commands
kubectl annotate pod my-first-pod owner=team-payments
kubectl describe pod my-first-pod | grep Annotations

ResourceQuota

Resource Management

Definition: Limits the total amount of compute resources (CPU, memory) or object count (number of Pods, Services) that can be consumed within a single namespace.

💡 Think of it like: a shared office's total electricity budget per floor — no single team can hog so much power that other teams on the same floor get cut off.

resourcequota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: staging
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
Commands
kubectl apply -f resourcequota.yaml
kubectl describe resourcequota team-quota -n staging

LimitRange

Resource Management

Definition: Sets default, minimum, and maximum CPU/memory requests and limits for individual Pods/containers within a namespace — so nobody accidentally deploys a container with no resource limits, or requests an unreasonable amount.

💡 Think of it like: a "one plate per person" rule at a buffet — a ResourceQuota caps the whole room's food, while a LimitRange caps how much any single plate can hold.

limitrange.yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: staging
spec:
  limits:
    - default:
        cpu: "500m"
        memory: 256Mi
      defaultRequest:
        cpu: "100m"
        memory: 128Mi
      type: Container
Commands
kubectl apply -f limitrange.yaml
kubectl describe limitrange default-limits -n staging

📈 Scaling & Autoscaling

Let Kubernetes automatically match capacity to demand.

Horizontal Pod Autoscaler (HPA)

Scaling

Definition: Automatically increases or decreases the number of Pod replicas in a Deployment/StatefulSet based on observed metrics — typically CPU or memory usage, or a custom metric.

💡 Think of it like: a restaurant manager who calls in extra waitstaff when it gets busy, and sends people home when it's quiet — reacting to demand ("horizontal" = more/fewer workers), not making one waiter work faster.

hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
Commands
kubectl apply -f hpa.yaml

# Quick imperative version
kubectl autoscale deployment nginx-deployment --cpu-percent=70 --min=2 --max=10

kubectl get hpa
kubectl describe hpa nginx-hpa

Vertical Pod Autoscaler (VPA)

Scaling

Definition: Automatically adjusts the CPU/memory requests and limits of containers based on actual usage over time, instead of the number of replicas. Not installed by default — it's a separate add-on.

💡 Think of it like: giving one waiter a bigger tray as they prove they can handle more ("vertical" = bigger, not more workers) — the opposite adjustment style from HPA.

⚠️ Don't run HPA (on CPU/memory) and VPA on the exact same metric for the same workload — they can fight each other.
vpa.yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: nginx-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx-deployment
  updatePolicy:
    updateMode: "Auto"

Cluster Autoscaler

Scaling

Definition: Automatically adds or removes nodes (whole machines) from the cluster based on whether there are Pods that can't be scheduled due to insufficient resources, or nodes sitting mostly idle.

💡 Think of it like: the restaurant manager renting an extra dining room down the hall when even fully-staffed existing rooms are overflowing — this scales the building itself, not just the staff inside it.

💡 HPA/VPA scale within existing nodes. Cluster Autoscaler scales the nodes themselves — they work together: HPA adds Pods → those Pods can't fit → Cluster Autoscaler adds a node.

🔐 Security & Access Control

Control who (and what) can do what, inside and outside the cluster.

RBAC (Role-Based Access Control)

Security

Definition: Controls who can perform which actions (get, list, create, delete...) on which resources. A Role defines permissions within one namespace; a ClusterRole defines permissions cluster-wide. A RoleBinding/ClusterRoleBinding then grants that role to a user, group, or ServiceAccount.

💡 Think of it like: a hotel keycard system. A Role is "what a keycard can unlock" (e.g. floor 3 only); a RoleBinding is "issuing that specific keycard to this specific guest."

role.yaml — Role + RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: staging
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: staging
subjects:
  - kind: User
    name: priya@example.com
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
Commands
kubectl apply -f role.yaml
kubectl get roles,rolebindings -n staging

# Check if you (or another user) can perform an action
kubectl auth can-i delete pods -n staging
kubectl auth can-i delete pods --as=priya@example.com -n staging

Service Account

Security

Definition: An identity for processes running inside Pods (as opposed to a User Account, which is for humans). It lets a Pod authenticate to the Kubernetes API — e.g. a controller Pod that needs to list other Pods.

💡 Think of it like: a staff badge for a robot/vending machine, versus a human employee's ID badge. The "user" here is a piece of software, not a person, but it still needs an identity and permissions.

Commands
kubectl create serviceaccount app-sa
kubectl get serviceaccounts
Using it in a Pod
spec:
  serviceAccountName: app-sa
  containers:
    - name: app
      image: my-app:1.0

Security Context

Security

Definition: Settings on a Pod or container that control privilege and access — e.g. run as a non-root user, make the filesystem read-only, or drop Linux capabilities.

💡 Think of it like: giving a contractor working in your house a "guest" key instead of the master key — they can do their job without the ability to unlock every door in the building.

Example
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
  containers:
    - name: app
      image: my-app:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]

🧰 Ecosystem

Popular tools built on top of Kubernetes.

Helm

Package Manager

Definition: The most popular package manager for Kubernetes. A "Chart" bundles a whole application's YAML manifests (Deployments, Services, ConfigMaps...) into one reusable, configurable, versioned package.

💡 Think of it like: apt install or npm install, but for entire applications on Kubernetes — instead of hand-writing 15 YAML files for a database, you run one Helm install command with your custom settings.

Commands
# Add a chart repository
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Install a chart as a "release"
helm install my-db bitnami/postgresql

# See what's installed
helm list

# Upgrade a release with new values
helm upgrade my-db bitnami/postgresql --set auth.password=newpass

# Roll back
helm rollback my-db 1

# Uninstall
helm uninstall my-db

🛠️ Troubleshooting

A short playbook for "why isn't this working" moments.

SymptomWhat to check
Pod stuck in Pendingkubectl describe pod <name> → look for scheduling events. Usually: not enough CPU/memory on any node, or an unsatisfied node selector/affinity/taint.
Pod in CrashLoopBackOffkubectl logs <pod> --previous to see why the last attempt died — usually an app error or failed startup/liveness probe.
Pod in ImagePullBackOffCheck the image name/tag for typos, verify the registry is reachable, and check imagePullSecrets for private registries.
Pod Running but app unreachableCheck the Service's selector matches the Pod's labels; confirm targetPort matches the container's actual listening port.
"0/3 nodes are available" in eventskubectl describe node <name> to see resource pressure, taints, or disk pressure conditions.
Service has no endpointskubectl get endpoints <service> — empty means no Pods matched the selector or none are Ready yet.
Need to see everything happening right nowkubectl get events -A --sort-by=.lastTimestamp

✅ Best Practices

Habits that separate a toy cluster from a production-ready one.

  • Always set resource requests and limits — an app with no limits can starve its neighbors of CPU/memory on the same node.
  • Use liveness & readiness probes — so Kubernetes knows when to restart a stuck container (liveness) vs. when to stop sending it traffic temporarily (readiness).
  • Never use :latest as an image tag in production — pin a specific version so rollouts and rollbacks are predictable.
  • Prefer Deployments over bare Pods — you get self-healing and rolling updates for free.
  • Keep secrets out of images and Git — use Secrets (or an external secrets manager), never bake credentials into a Dockerfile.
  • Use namespaces to separate environments — don't run dev and prod workloads mixed in the same namespace.
  • Apply the principle of least privilege with RBAC — don't grant cluster-admin when a scoped Role would do.
  • Store manifests in version control — treat YAML like code (GitOps): review, diff, and roll back through Git history.
  • Run kubectl apply --dry-run=client before applying unfamiliar changes — catch typos before they hit the cluster.
